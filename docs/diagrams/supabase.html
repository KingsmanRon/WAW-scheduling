ACCESS on Supabase

Supabase holds everything ACCESS remembers: staff sign-in, the database, encrypted referral documents and live updates. Only the API, the worker and the migration job connect to the database, each with its own login, and the browser has no way in.

What the database itself enforces

  • No double bookings. An exclusion constraint (appointments_no_practitioner_overlap) refuses any appointment that overlaps another for the same practitioner, however the request arrived. Working hours can't overlap either.
  • Each practice sees only its own rows. Row-level security on every practice table. Each transaction states its organisation and practice; with nothing stated, it sees nothing.
  • The audit trail can't be rewritten. Triggers refuse any update, delete or truncate of audit_events.
  • Nothing is lost between a change and its follow-up. The outbox row is saved in the same transaction as the appointment, so a confirmation is never sent for a booking that failed, nor skipped for one that succeeded.
  • Logins hold only what they need. The API and worker logins can't bypass row-level security and own nothing; only the migration job's owner login can change the schema.

Setting up the project

  1. Create the project in the approved region and turn on point-in-time recovery.
  2. In Auth, turn public sign-ups off and add the staff accounts.
  3. Deploy the Railway migrate service; it applies supabase/migrations in order and stops.
  4. Run runtime-roles.sql once to give the API and worker their logins.
  5. Run storage-bucket.sql once to create the private documents bucket.
  6. Turn the Data API off (or remove public from it); ACCESS never uses it.

The exact commands are in DEPLOYMENT.md, section 1. Staging and production are separate projects, and staging never holds real patient data.
